# dev-flow

스펙으로 무엇을 만들지 고정하고, 계획과 태스크로 쪼개고, 테스트를 먼저 쓰고, 구현하고, 여러 관점으로 검증한다.
우선순위는 AGENTS.md 를 따른다: 결과물 > 증거 > 설명 > 시간 > 효율.

## 핵심 규칙: 단계마다 사용자 승인

각 STEP 이 끝나면 아래 형식을 출력하고 멈춘다.
```
[GATE N] STEP N 완료 - 사용자 승인 필요 (경과 약 M분 / 계획 K분)
"진행해" / "다음" / "OK" 를 입력하면 STEP N+1 로 넘어갑니다. 수정할 점이 있으면 말씀해 주세요.
```
- 명시적 승인 없이 다음 STEP 으로 가지 않는다. 승인 말: 진행해, 다음, OK, 응, ㅇㅇ, 계속.
- 수정 요청을 받으면 현재 STEP 을 다시 한다.
- GATE 를 건너뛰었으면 즉시 그 STEP 으로 돌아가 GATE 를 출력한다.
- GATE 마다 경과 시간과 계획 시간을 함께 적는다. 늦어졌으면 범위를 줄이는 안을 함께 낸다.

계획 시간(180분 기준): GATE1~3 20분 / GATE4 25분 / 첫 완주 70분 / GATE5(기능 추가 멈춤) 120분 / GATE6 145분 / 제출 165분.
- 3시간은 짧다. GATE 1~3 은 각각 10줄 이내로 짧게 출력해 사람이 1분 안에 읽고 넘길 수 있게 한다.
- 120분이 되면 개선 태스크가 남아도 기능 추가를 멈추고 STEP 6 으로 간다. 남은 태스크는 TASK.md 7번(하지 못한 것)으로.

---

## STEP 1. 스펙 (역질문 먼저, 코드 금지)

1. 과제 README, 파일 목록, 데이터 형식, 제출 형식을 읽는다. 데이터는 `python3 ~/codex-harness/tools/peek.py <파일>` 로 구조만 본다.
2. 바로 쓰지 않고, 불명확한 항목을 골라 한 번에 역질문한다.
   - 누가 결과를 보고 어떤 결정을 하나 / 입력 형식과 제약 / 예외와 빈 값 / 기준값과 같으면 통과인가 / 성공을 어떤 숫자로 아나 / 완료 기준
   - 담당자(DM 의 AI 나 사람)가 있으면 `~/codex-harness/docs/담당자_인터뷰.md` 순서로 질문 목록을 만들어 사람에게 넘긴다. 유도 질문은 쓰지 않는다.
3. 답을 받으면 `TASK.md` 를 스펙으로 채운다: 한 문장, **범위 세 칸(필수 / 개선 / 안 함)**, 사실(출처), 가정(틀리면 무엇이 깨지나), 열린 질문, 안 할 일, 완료 조건(측정 가능한 문장). 합의문은 `DECISIONS.md` 맨 위에.
   - 필수: 없으면 제출 기준 미달. 개선: 점수는 오르지만 없어도 제출 가능. 안 함: 이유 한 줄(서술형 답이 된다).
   - 필수가 70분 안에 끝나지 않을 크기면 지금 줄이는 안을 낸다.
4. 과제 유형에 맞는 스킬을 정한다: 표 데이터 판정이면 `$data-judge`, 결과물이 LLM 을 부르면 `$llm-feature`, 웹 화면이면 `$web-ui`.

GATE 1 출력: 목적 / 범위 세 칸 / 입력과 출력 / 엣지 케이스 / 완료 조건 / 쓸 스킬 요약.

## STEP 2. 계획 (`specs/plan.md`)

- 구조: 입력 > 처리 > 출력의 흐름, 모듈과 파일 나눔.
- 기술: 이미 설치된 것 우선(Python 3.11, pandas, pytest). 없으면 설치를 한 번 시도하고 결과를 기록한다.
- 인터페이스: 함수, CLI, API 의 입출력 형태. 데이터 모델.
- 제약: 시간, 성능, 보안, 키 관리.
- **첫 완주 경로**: 규칙을 다 채우지 않고 입력부터 제출 파일까지 가는 가장 짧은 길.
- 선택마다 버린 대안과 이유를 `DECISIONS.md` 에 한 줄.

GATE 2 출력: 구조 / 주요 기술 / 인터페이스 / 첫 완주 경로 요약.

## STEP 3. 태스크 분해 (`specs/tasks.md`)

- 각 태스크는 혼자 구현, 테스트할 수 있는 단위. 순서와 의존 관계를 적는다.
- 각 태스크에 완료 기준과 테스트 이름(`test_...`)을 붙인다. `TASK.md` 완료 조건과 1:1 로 이어지게 한다.
- **태스크 1 은 항상 첫 완주(end-to-end)** 다.
- 태스크에 우선순위(필수 / 개선)를 붙인다. 시간이 모자라면 개선부터 뺀다.

GATE 3 출력: 태스크 목록(번호, 내용, 완료 기준, 테스트 이름, 필수/개선).

## STEP 4. 테스트 먼저 (TDD)

- 완료 기준을 테스트로 옮긴다. pytest(`python3 -m pytest -q`).
- 실행해서 **실패하는 것을 확인**하고 출력을 보여준다. 실패를 본 적 없는 테스트의 통과는 믿지 않는다.
- 기대값은 코드와 같은 방법으로 만들지 않는다. 원본에서 따로 구하거나 손으로 계산한 작은 표본을 쓴다.

GATE 4 출력: 테스트 목록 / 실행 결과(전체 N 개 실패 확인).

## STEP 5. 구현

- AGENTS.md 의 코드 원칙을 따른다(요구사항 먼저, 표준 도구 우선, 경계값 주석, 입력 변경 금지, 에러 삼키지 않기, 근본 원인 수정).
- 태스크 순서대로: 최소 구현 > 테스트 통과 > 출력 직접 확인 > 커밋. 커밋마다 "이 변경이 어떻게 동작하는지" 한국어 3줄을 사람에게 보여준다.
- 태스크 1(첫 완주)이 통과하면 바로 커밋하고 "제출 가능 상태"라고 알린다. 70분까지 안 되면 멈추고 범위를 줄이는 안 2개와 추천을 낸다.
- 과제에 뼈대가 없고 웹 서버, Docker 가 필요하면 `~/codex-harness/templates/app/` 를 복사해 시작한다(`cp -rn ~/codex-harness/templates/app/. .`).
- **태스크마다 `UNDERSTANDING.md` 에 한 칸**: 만든 것(파일:함수) / 입력 > 처리 > 출력 / 가정 / 확인(테스트 이름, 결과 숫자) / 못 한 것. 그리고 사람에게 "이 태스크를 한 줄로 설명해 주세요"라고 묻고, 그 설명이 코드와 맞는지 파일:줄로 답한다. 틀린 부분만 짚는다.
- 막히면 `$systematic-debugging`. 15분 넘게 막히면 독립 세션(`codex exec --sandbox read-only`)에 원인 조사를 맡기거나 `/model` 로 모델을 바꿔 다시 본다. 30분이 넘으면 범위 조정을 사람에게 묻는다.
- 문제를 해결할 때마다 `DECISIONS.md` '디버깅 기록'에 4칸(`$systematic-debugging` 5절). 과제가 `AI_COLLABORATION.md` 를 요구하면 거기에도.
- AI 가 틀렸다가 확인으로 잡힌 순간은 `DECISIONS.md` 'Codex 를 믿지 않은 순간'에 한 줄.

GATE 5 출력: 바뀐 파일 / 구현 요약 / 테스트 재실행 결과(전체 N 개 통과) / 남은 개선 태스크.

## STEP 6. 리뷰와 품질 올리기 (7개 관점, 120~145분)

원래는 리뷰 에이전트 7개를 병렬로 돌렸다. Codex 에서는 메인 세션의 `$review-checklist` 와, 별도 터미널의 독립 세션 리뷰로 같은 7개 관점을 덮는다. 독립 세션은 찾기만 하고, 수정은 메인 세션에서만 한다.

| 관점 | 볼 것 |
|---|---|
| 코드 | 정확성, 로직 오류, 중복, 불필요한 복잡성, 완료 조건 충족 |
| 보안 | 비밀값, 인젝션, 경로 조작, 검증 안 한 외부 입력 |
| 데이터 | 빈 값, 중복, 경계값, 단위, 정렬, 제외 행 건수와 전후 합계 (DB 가 있으면 쿼리, 트랜잭션) |
| 무음 실패 | 빈 except, 실패를 숨기는 기본값, 로그 없는 예외 |
| 성능 | 루프 안 반복 I/O, 전체 재계산, 데이터 크기에 맞지 않는 방법 |
| 사용성, 접근성 | 담당자가 결과를 바로 쓰나, 오류와 빈 결과 안내, (화면이면) label, 키보드, 대비 |
| 계약 | 함수, API, 화면 사이 입출력 형태, 필드명, 상태코드 일치. 한쪽만 있으면 해당 없음 |

사람에게 독립 리뷰 명령을 안내한다(새 터미널 탭에서, 동시에 돌려도 된다):
```
codex exec --sandbox read-only "코드, 무음 실패 관점: TASK.md 완료 조건과 코드를 대조해 틀릴 수 있는 계산, 빠진 요구사항, 실패를 숨기는 곳을 파일:줄과 함께 찾아. 고치지는 마."
codex exec --sandbox read-only "보안, 데이터 관점: 비밀값, 검증 안 한 입력, 빈 값, 중복, 경계값, 단위에서 결과가 틀어질 수 있는 곳을 파일:줄과 함께 찾아. 고치지는 마."
codex exec --sandbox read-only "성능, 사용성, 계약 관점: 느려질 곳, 담당자가 결과를 바로 쓰기 어려운 점, 모듈 사이 입출력 불일치를 파일:줄과 함께 찾아. 고치지는 마."
```
- 독립 리뷰를 띄워 둔 동안 메인 세션은 `UNDERSTANDING.md` 와 README 를 정리한다(기다리지 않는다).
- 결과를 받으면 맞는지 확인하고, 맞는 것만 고친다. CRITICAL, HIGH 는 반드시. MEDIUM 은 시간이 있으면, 남기면 `TASK.md` 7번에 이유. 고칠 때마다 테스트와 커밋.
- 담당자 입장에서 시나리오를 처음부터 끝까지 써 보고 불편한 점을 우선순위대로 고친다.

GATE 6 출력:
```
관점별 점검: 코드 [x] 보안 [x] 데이터 [x] 무음 실패 [x] 성능 [x] 사용성 [x] 계약 [x 또는 해당 없음]
CRITICAL N / HIGH N / MEDIUM N / LOW N (고친 것 N, 남긴 것과 이유)
테스트 재실행 결과
```
체크리스트에 빈 칸이 있으면 그 관점을 바로 점검하고 다시 보고한다.

## STEP 7. 동결과 제출 준비 (145분부터, 기능 추가 금지)

- `$verify` 로 증거 대조(PASS / FAIL / NOT_RUN / HUMAN_CHECK).
- README 를 심사자용으로: 무엇을 만들었나 / 하지 않은 것 / 실행 방법(실제로 쳐 본 명령만) / 현재 상태(숫자) / 내가 정한 것과 이유 / 하지 못한 것과 이유.
- `TASK.md` 6번(내가 정한 것), 7번(하지 못한 것)을 채운다.
- `UNDERSTANDING.md` 를 사람이 처음부터 읽게 하고, 설명이 막히는 줄을 받아 그 부분만 코드 기준으로 다시 설명한다. 맨 위에 "구현하고 검증한 것 / 가정으로 둔 것 / 하지 않은 것 / 평가자가 확인할 경로" 요약 4줄을 채운다.
- `DECISIONS.md` 맨 아래 '서술형 카드' 15줄: 한 문장 요약, 사용자와 돕는 결정, 핵심 결정 3개(이유, 버린 대안), 지킨 조건과 조정한 것, 가정 2개, 검증 숫자, 가장 약한 입력, Codex 를 믿지 않은 순간, 안 한 것, 시간이 두 배라면, 데이터 흐름과 상태 저장 위치, 평가자 확인 경로, 디버깅 기록 대표 1건. 각 줄에 근거 파일:줄 또는 커밋. 근거 없는 내용은 쓰지 않는다.
- `python3 ~/codex-harness/scripts/preflight.py submit` 를 돌리고 `git status` 가 깨끗한지 확인한다.

최종 보고: verify 결과 / preflight 결과 / 서술형 카드 위치 / "제출 가능합니다".

## 흐름 요약
```
STEP 1 스펙(역질문, TASK.md)          > GATE 1
STEP 2 계획(specs/plan.md)            > GATE 2
STEP 3 태스크(specs/tasks.md)         > GATE 3
STEP 4 테스트 먼저, 실패 확인          > GATE 4
STEP 5 구현(첫 완주 70분, 태스크별 커밋, 120분 기능 멈춤) > GATE 5
STEP 6 7개 관점 리뷰와 품질 올리기      > GATE 6
STEP 7 동결, verify, README, 서술형 카드 > 제출
```
