# systematic-debugging

철칙: 근본 원인을 조사하기 전에는 고치지 않는다. 급할수록 이 절차가 더 빠르다.

## 1. 원인 조사
1. 에러 메시지와 스택트레이스를 끝까지 읽는다. 줄 번호, 에러 코드.
2. 재현 조건을 확정한다. 재현이 안 되면 추측하지 말고 증거를 더 모은다.
3. 최근 변경을 본다: `git diff`, `git log -5`.
4. 여러 단계가 이어진 흐름이면 단계 경계마다 입출력을 출력해 어디서 깨지는지 먼저 찾는다.
5. 잘못된 값은 처음 생긴 곳까지 거슬러 올라가 거기서 고친다.

## 2. 패턴 비교
- 같은 코드에서 정상 동작하는 비슷한 예를 찾아 차이를 전부 나열한다.

## 3. 가설과 최소 검증
- "X 가 원인이다, 왜냐하면 Y" 로 적는다.
- 한 번에 변수 하나만 바꿔 확인한다. 실패한 수정 위에 덧붙이지 않는다(되돌리고 새 가설).

## 4. 수정
1. 실패하는 테스트나 재현 스크립트를 먼저 만든다.
2. 원인 하나만 고친다. 김에 하는 리팩터링 금지.
3. 전체 테스트를 다시 돌린다.
4. 3번 실패하면 4번째 수정을 하지 말고 구조를 의심한다. 사용자에게 현황을 보고하고 방향을 묻는다.

## 5. 기록 (서술형 재료, 빼먹지 않는다)
해결하면 `DECISIONS.md` '디버깅 기록'에 4칸 한 줄. 과제가 `AI_COLLABORATION.md` 같은 AI 협업 기록을 요구하면 같은 4칸으로 그 파일에도 쓴다.
`발견: 어떻게 알았나 / AI 진단: 무엇이라고 했나 / 받아들임, 고침, 버림: 무엇을 왜 / 확인: 명령과 결과 숫자`
버린 가설도 한 줄 남긴다. 서술형은 "그 문제를 어떻게 발견했고, AI 진단 중 무엇을 받아들이거나 버렸고, 근거로 어떤 실행 결과를 봤나"를 그대로 묻는다.
