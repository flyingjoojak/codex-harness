스킬 8개 (Codex 에 "$이름" 으로 부른다. 안 되면 ".agents/skills/<이름>/SKILL.md 읽고 따라")
================================================================
$dev-flow             전체 흐름. 스펙(역질문) > 계획 > 태스크 > 테스트 > 구현 > 7관점 리뷰 > 동결. 단계마다 GATE 에서 멈추고 내 승인을 받는다.
                      언제: 시작할 때 한 번(첫 프롬프트에 들어 있음). 흐름이 흐트러지면 다시.
$data-judge           표 데이터 판정, 집계, 순위. 기준표 확정 > 규칙 코드 > 행마다 사유 > 다른 방법으로 대조.
                      언제: 과제가 CSV 등 데이터를 기준으로 판정, 분류, 집계할 때. 계약 단계에서.
$llm-feature          결과물 안에서 LLM API 호출. 연결 확인 > 규칙 먼저 > 대체 경로 > 출력 검증 > 네트워크 없는 테스트.
                      언제: 요약, 분류, 문구 생성 등 결과물이 LLM 을 불러야 할 때. 계약 단계에서.
$web-ui               업무 도구 화면. AI 티 금지, 핵심 결과 먼저, 상태 문구, 시나리오 확인.
                      언제: 웹 화면이 필요할 때. 첫 완주 뒤, 품질 올리기 구간에서 완성도.
$systematic-debugging 근본 원인부터 4단계. 원인 조사 > 패턴 비교 > 가설 하나씩 > 테스트 먼저 수정.
                      언제: 버그, 테스트 실패, 같은 오류 2번, 이상한 결과.
$review-checklist     자체 리뷰. 정확성, 무음 실패, 보안, 성능, 계약, 데이터, 단순성, 사용성, 설명.
                      언제: 리뷰 구간, 140분 점검. CRITICAL, HIGH 수정(MEDIUM 은 시간 되면).
$verify               제출 전 증거 대조. 테스트 전체, 실제 실행, 완료 조건 표, 숫자 재확인, README, preflight.
                      언제: 140분 점검, 제출 직전. 결과가 PASS/FAIL/NOT_RUN/HUMAN_CHECK 숫자로 나온다.
$essay-mock           서술형 모의. 제출물을 읽고 출제자처럼 6문항 > 내가 AI 없이 답 > 코드와 대조해 채점.
                      언제: 동결 구간, 서술형 카드를 만든 뒤(10분). 제출물 속 설명 못 하는 문장을 찾는 용도.

GATE 지도 (dev-flow 가 멈추는 곳. "진행해" 로 넘긴다. 수정할 점은 그때 말한다)
================================================================
3시간은 짧다. GATE 1~3 은 읽고 "진행해"로 1분 안에 넘긴다. 시간을 쓸 곳은 범위 결정과 이해 확인이다.
GATE 1 (~10분)  스펙: 범위 세 칸(필수/개선/안 함)이 있나, 필수가 70분 안에 될 크기인가, 담당자 답 반영
GATE 2 (~15분)  계획: 구조가 단순한가, 첫 완주 경로가 짧은가
GATE 3 (~20분)  태스크: 태스크 1 이 첫 완주인가, 테스트 이름, 필수/개선 표시
GATE 4 (~25분)  테스트: 실제로 실패하는 것을 보여줬나
첫 완주 (~70분) 필수 기능 end-to-end. Docker 요구면 Docker 실행까지
GATE 5 (~120분) 기능 추가 멈춤. 테스트 전체 통과, UNDERSTANDING.md 가 태스크마다 찼나
GATE 6 (~145분) 리뷰: 7개 관점, CRITICAL/HIGH 처리(MEDIUM 은 남기면 이유)
STEP 7 (145분~) 동결: UNDERSTANDING 확인, 서술형 카드, verify, README, preflight > 제출
늦어지면 GATE 에서 Codex 가 범위 줄이는 안을 낸다. 고르는 건 나다.

================================================================

   "AGENTS.md 를 따른다. 적용한 지침을 3줄로 요약한 뒤 $dev-flow 1단계부터 시작해. 아직 코드는 쓰지 마."
4) 확인할 것
   - 3줄 요약에 "결과물 우선", "증거 규칙", "계약 먼저" 같은 내용이 나오면 정상.
   - 요약이 엉뚱하면: "AGENTS.md 를 다시 읽고 요약해" 한 번 더.
5) 과제 화면의 README 를 나도 직접 한 번 읽는다(5분). 제출 형식과 금지 사항에 줄을 긋는다.
6) git 작성자 확인: setup.sh 출력 맨 아래 "git 작성자:" 줄을 본다.
   - 비어 있었으면 setup.sh 가 이 폴더에만 자동 설정했다. 따로 할 일 없음.

     git config user.email "flyingjoojak@users.noreply.github.com"

[5~20분] 계약과 범위 (코드 금지 구간)
================================================================
Codex 가 하는 일: 과제를 읽고 역질문을 낸 뒤, 답을 받아 TASK.md 를 채우고 GATE 1 에서 멈춘다.
이후 GATE 2(계획), GATE 3(태스크), GATE 4(테스트 실패 확인)가 이어진다. 각각 보고 "진행해".

내가 하는 일
1) TASK.md 를 직접 연다: cat TASK.md
2) 확인할 것
   - 0번 범위: 필수가 정말 "없으면 제출 기준 미달"인 것만인가. 70분 안에 될 크기인가.
     크면: "필수를 70분 안에 끝낼 수 있게 줄이는 안을 내. 뺀 것은 개선이나 안 함으로."
   - "한 문장"이 과제 README 와 맞는가
   - "사실" 칸에 과제에 없는 말이 들어가 있지 않은가(있으면 가정으로 옮기라고 지시)
   - "안 할 일"이 비어 있지 않은가
   - "완료 조건"마다 test_ 이름이 붙어 있는가
3) 담당자 DM
   - Codex 가 준 "열린 질문"을 DM 담당자에게 한두 개씩 보낸다.
   - 질문 요령: 업무 장면을 짚는다. "할 일을 알려주세요"는 쓰지 않는다.
     예) "이 결과는 누가 보고 어떤 결정을 하나요?"
         "값이 비어 있는 기록은 어떤 상태이고, 결과에 어떻게 반영해야 하나요?"
         "기준값과 정확히 같으면 통과인가요?"
         "놓치는 것과 잘못 잡는 것 중 어느 쪽이 더 곤란한가요?"
   - 막혔을 때: "과제 맥락을 정확히 이해하고 싶습니다. 현업 관점에서 제가 먼저 확인해야 할 것이 무엇일까요?"
4) 받은 답을 Codex 에 붙여넣기:
   "담당자 답변이다. TASK.md 사실/가정 표와 DECISIONS.md 합의문에 반영해: (답변 붙여넣기)"
5) 과제 유형에 맞는 스킬을 함께 부른다:
   - 표 데이터 판정, 집계, 순위: "$data-judge 를 따라 기준표부터 TASK.md 에 정리해."
   - 결과물 안에서 LLM 을 불러야 함: "$llm-feature 를 따라 연결 확인부터 해. 키 값은 출력하지 마."
   - 웹 화면이 필요함: 화면은 첫 완주 뒤에 $web-ui 로(아래 70~120분 참고).
6) 다 맞으면: "진행해"

[20~70분] 첫 완주 (필수만)
================================================================
목표: 규칙이 덜 채워져도 입력 > 처리 > 제출 파일까지 한 번 끝까지 돈다.

Codex 에게: (dev-flow 가 알아서 하지만 흐트러지면)
   "규칙은 나중에. 입력부터 제출 파일 생성까지 끝까지 한 번 돌아가는 최소본을 만들고, 실행 결과를 보여준 뒤 커밋해. 그다음 멈춰."

뼈대가 없고 웹 서버나 Docker 가 필요하면(과제에 이미 구조가 있으면 그것을 쓴다):
   cp -rn ~/codex-harness/templates/app/. .
   "templates 에서 복사한 뼈대(app/server.py, Dockerfile, tests/test_server.py)를 바탕으로 첫 완주를 만들어."

내가 확인할 것
- 제출 파일이 실제로 생겼는가: ls 로 직접 본다.
- 형식(파일명, 열 이름, 개수)이 과제 요구와 맞는가.
- git log --oneline 에 커밋이 있는가.

70분 점검: "STATE"
- 첫 완주가 안 됐으면: "남은 시간 기준으로 범위를 줄이는 안을 2개 내고 추천해."

[70~120분] 개선 (120분에 기능 추가 멈춤)
================================================================
반복 단위: 완료 조건 하나 > 테스트 작성 > 실패 확인 > 구현 > 통과 > 커밋.

Codex 에게 작게 맡기기:
   "TASK.md 완료 조건 N번을 test_xxx 로 만들고, 실패하는 것을 먼저 보여줘. 그다음 통과하게 구현하고 커밋해. 다른 파일은 건드리지 마."

태스크를 끝낼 때마다(서술형 재료, 3분. 마지막에 몰아 하면 못 한다):
   "방금 태스크를 UNDERSTANDING.md 에 한 칸 추가해: 만든 것(파일:함수) / 입력 > 처리 > 출력 / 가정 / 확인(테스트, 숫자) / 못 한 것."
   > 내가 한 줄로 설명을 쳐 본다: "내 설명: (한 줄). 코드와 맞는지 파일:줄로 확인하고 틀린 곳만 짚어."
   > 막히면 그 줄이 서술형에서 막힐 줄이다. 바로 물어서 이해하고 넘어간다.

120분이 되면: 개선이 남아도 멈춘다.
   "기능 추가는 여기까지. 남은 개선 태스크를 TASK.md 7번에 이유와 함께 옮기고 커밋해."

의심해야 할 때 쓸 문장:
   "이 결론이 틀렸다면 데이터 어디서 드러날지 찾아서 실제로 확인해."
   "기대값은 코드와 같은 방법으로 계산하지 말고 원본에서 따로 구해서 비교해."
   "제외하거나 변환한 행이 있으면 건수와 처리 전후 합계를 같이 보여줘."
   "합의한 요구사항과 지금 구현을 대조해서, 없는데 들어간 것과 빠진 것을 표로 보여줘."

AI 가 틀린 것을 잡았을 때:
   "방금 일을 DECISIONS.md 의 'Codex 를 믿지 않은 순간'에 한 줄 적어."

문제를 하나 해결할 때마다(1회차 서술형 6번이 그대로 물었다):
   "방금 문제를 DECISIONS.md '디버깅 기록'에 4칸으로 적어: 발견 / AI 진단 / 받아들임, 고침, 버림(이유) / 확인(명령과 결과 숫자). 과제가 AI_COLLABORATION.md 를 요구하면 거기에도."

같은 오류로 두 번 실패하면:
   "고치지 말고 원인 가설 두 개와 확인 방법을 먼저 말해." (또는 $systematic-debugging)

15분 넘게 한 기능에 막히면:
   - 새 터미널에서 독립 세션에 원인 조사: codex exec --sandbox read-only "이 오류의 원인 가설과 확인 방법을 찾아. 고치지는 마: (오류 붙여넣기)"
   - 또는 /model 로 모델을 바꿔 다시 보기
   - 30분이 넘으면 범위를 조정할지 내가 정한다. 빼기로 하면: "이 기능은 TASK.md 안 할 일로 옮기고 이유를 적어."

엣지 케이스(시간이 남으면): 빈 값, 0, 경계값, 중복, 순서, 형식 오류.

웹 화면이 필요한 과제면:
   "$web-ui 를 따라 화면을 만들어. 첫 화면에 핵심 결과를 바로 보여주고, 담당자가 바로 쓰기 좋게 다듬어."
   - 첫 완주는 기능 위주. 화면 완성도는 품질 올리기 구간에서 끌어올린다.
   - 확인: 내장 브라우저로 담당자 시나리오 하나를 끝까지 따라가 본다.

AI 를 더 쓸 때 (품질에 도움이 되면 쓴다. 쓴 이유는 DECISIONS.md 에 한 줄):
   - 낯선 라이브러리 API 를 Codex 가 지어내면: Context7 MCP 연결(시험 화면 MCP 설정, 5분 안에 안 되면 포기)
   - 설계가 갈릴 때: /model 로 다른 모델로 바꿔 "반대 입장에서 이 설계의 약점을 말해" > 다시 원래 모델로
   - 첫 완주 뒤, 그리고 140분에: 아래 "독립 리뷰"

[120~140분] 리뷰와 품질 (개선을 다 채웠으면 더 일찍 시작)
================================================================
결과물이 최우선이다. 토큰을 아끼려고 이 구간을 줄이지 않는다.
   "담당자 입장에서 이 결과물을 처음부터 끝까지 써 보고, 불편한 점, 틀릴 수 있는 점, 빠진 점을 우선순위로 5개 뽑아. 근거는 파일:줄이나 실행 결과로."
   > 위에서부터 하나씩 고치고, 고칠 때마다 테스트와 커밋.

관점별 독립 리뷰 (새 터미널 탭 여러 개를 동시에 써도 된다. 각자 고치지는 않는다):
   codex exec --sandbox read-only "정확성 관점: TASK.md 완료 조건과 코드를 대조해 틀릴 수 있는 계산과 빠진 요구사항을 파일:줄과 함께 찾아. 고치지는 마."
   codex exec --sandbox read-only "데이터 관점: 빈 값, 중복, 경계값, 단위, 정렬에서 결과가 틀어질 수 있는 곳을 파일:줄과 함께 찾아. 고치지는 마."
   codex exec --sandbox read-only "사용성 관점: 담당자가 결과를 보고 바로 결정할 수 있는지, 오류와 빈 결과 안내가 있는지 보고 개선점을 찾아. 고치지는 마."
   > 리뷰가 도는 동안 메인 Codex 는: "UNDERSTANDING.md 맨 위 요약 4줄(구현하고 검증한 것 / 가정 / 하지 않은 것 / 평가자 확인 경로)을 채워."
   > 결과를 메인 Codex 에 붙여넣고: "이 지적이 맞는지 확인하고, 맞는 것만 우선순위대로 고쳐."

[140~145분] 점검

[서술형 6문항 x 5분] 답 순서
================================================================
AI, 복사, 붙여넣기 금지. 직접 타이핑. 이전 문항으로 못 돌아감. 문항당 5분.
5분 배분: 30초 질문 읽기 > 3분 쓰기 > 1분 숫자와 이름 다시 보기.

답 순서 (4문장이면 충분):
  1) 사실   "과제에는 X 라고만 되어 있었습니다." / "담당자는 Y 라고 답했습니다."
  2) 결정   "그래서 저는 Z 로 정했습니다."
  3) 근거   "이유는 A 이고, B 파일의 C 함수에서 처리하며, 테스트 N 개로 확인했습니다."
            (파일명, 함수명, 숫자를 넣는다. 서술형 카드에서 외운 것)
  4) 한계   "다만 D 인 경우에는 틀릴 수 있고, 고치려면 E 를 검증해야 합니다."

예시 답:
  "과제에는 기준값만 있고 같은 값일 때의 처리는 없었습니다. 담당자에게 물어
   같으면 통과로 정했습니다. judge.py 의 check 함수에서 이상(>=)으로 비교하고,
   경계값 테스트 3개(같음, 바로 아래, 바로 위)로 확인했습니다. 다만 소수점
   반올림 기준은 확인하지 못해, 원본이 반올림된 값이면 경계에서 틀릴 수 있습니다."

1회차에 나온 틀(공식 아님): 알고리즘 선택 근거와 한계 / 데이터 흐름 모듈과 상태 소유 / 구현한 것 vs 가정, 확인 경로 /
  조건이 바뀌면 추가 검증과 AI 결과 판단 근거 / AI 협업 기록의 특정 문제를 어떻게 발견하고 무엇을 받아들이거나 버렸나.

질문 유형별:
  - 약점을 물으면: 약한 지점 지목 > 왜 위험한가 > 다음에 무엇을 검증하겠나.
  - AI 활용을 물으면: 맡긴 것 > 직접 한 것 > AI 를 믿지 않고 확인한 순간(무엇을, 어떻게).
  - 다시 한다면을 물으면: 바꿀 것 하나 > 이유 > 그러면 무엇이 좋아지나.
  - 질문 전제가 틀렸으면 첫 문장에서 바로잡는다: "실제로는 X 가 아니라 Y 로 처리했습니다."

하지 말 것:
  - 코드에 없는 처리를 있다고 말하기, 숫자를 실제와 다르게 말하기
  - AI 탓, 시간 탓 > 대신 "X 를 안 할 일로 정했습니다. 이유는 Y 입니다."
  - 모르는 것을 아는 척 > 대신 "확인하지 않았습니다. 확인하려면 A 를 보면 됩니다."
