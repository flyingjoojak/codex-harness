# 통근 노선 생성 과제 대비

1회차 과제 모양(참가자 공개 기록, 공식 아님): 구성원, 정류장, 근무표 CSV 를 골라 검증하고 적용 > 정원과 도착 여유 조건을 지키는 노선 생성 > 구성원 화면에서 조회, 내보내기.
"정류장별 직행"이나 "차량 수만 줄이는 병합"이 아닌 방식을 요구했다. Docker 로 실행, 제출물에 `AI_COLLABORATION.md`.
재시험 과제는 다를 수 있다. 같거나 비슷하면 이 메모를 쓰고, 다르면 구조(기준선 > 개선 > 독립 검사기)만 가져간다.

참고 구현: `python3 ~/codex-harness/tools/route_ref.py` (표준 라이브러리, 자체 검사 포함). 과제 코드에 그대로 복사하지 말고 구조를 참고해 Codex 와 함께 다시 짠다. 생성 코드는 검토와 테스트 후에 쓴다.

## 1. 문제를 한 문장으로
근무 조마다(같은 도착 목표 시각), 정류장 탑승 인원을 차량 정원 안에서 묶어, 회사에 "근무 시작 - 여유" 시각까지 도착하는 노선을 만든다. 차량 수와 승객 탑승 시간 사이의 균형이 핵심이다.
교과서 이름: 정원과 시간 제약이 있는 차량 경로 문제(CVRP with time windows). 정확해는 어렵고 휴리스틱이 표준이다.

## 2. 담당자에게 물을 것 (첫 DM, 숫자로 묻는다)
- 우선순위: 차량 수를 줄이는 것과 승객 탑승 시간을 줄이는 것 중 무엇이 먼저인가. "차량 1대 줄이는 대신 승객 1인당 평균 몇 분까지 늘어도 되나요?"
- 최대 탑승 시간 제한이 있나. 같으면 허용인가.
- 도착 여유: 근무 시작 몇 분 전 도착인가. 너무 일찍 도착하는 것도 문제인가(대기 상한).
- 이동 시간: 시간 행렬이 있나, 좌표만 있나. 좌표면 속도 가정, 정차 시간은 몇 분인가.
- 차량 종류가 하나인가(정원 하나), 차고지 출발이 따로 있나.
- 퇴근 노선도 만드나(방향이 반대: 회사 출발, 근무 끝 + 여유 이후).
- 한 정류장 인원이 정원보다 많으면 나눠 태워도 되나.
- 야간 조(자정 넘김), 근무표에 없는 구성원, 정류장이 없는 구성원은 어떻게 처리하나.

## 3. 데이터 검증 (적용 전에, 제외 행은 건수와 사유를 화면에 보인다)
- 필수 열, 중복 ID, 빈 값, 존재하지 않는 정류장 참조, 근무표에 없는 구성원
- 좌표 범위, 시간 형식(`HH:MM`, 자정 넘김), 정원 0 이하
- 제외 전후 인원 합계 대조. 검증 실패한 데이터셋은 적용하지 않는다(이전 적용본 유지).

## 4. 알고리즘 (route_ref.py 순서)
1. 조별로 나눈다: 같은 근무 시작 시각 = 같은 도착 목표.
2. 정류장별 인원 집계. 정원 초과 정류장은 정원 단위로 나눈다.
3. 기준선 1 = 정류장별 직행. 모든 조건을 지키는 가장 단순한 계획.
4. 절약 병합(Clarke-Wright savings 변형): 두 노선을 이었을 때 비용이 가장 많이 줄어드는 쌍부터 합친다. 정원과 최대 탑승 시간을 넘으면 합치지 않는다.
   - 비용 = 차량 가중치 x 차량 수 + 승객 탑승 시간 합(승객-분). 차량 수만 보지 않는다. 가중치는 담당자 답으로 정한다.
5. 노선 안 순서 개선(2-opt): 순서를 뒤집어 비용이 줄면 바꾼다.
6. 정류장 옮기기(relocate): 정류장 하나를 다른 노선으로 옮겨 비용이 줄면 옮긴다.
7. 시간표: 도착 목표 시각에서 거꾸로 각 정류장 출발 시각을 계산한다.

버린 대안과 이유(서술형 1번 재료)
- 정류장별 직행: 조건은 지키지만 차량이 많다. 기준선으로만 쓴다.
- 차량 수만 줄이는 병합: 승객이 크게 돌아간다(최대 탑승 시간이 늘어난다). 가중치를 아주 크게 준 경우로 비교한다.
- OR-Tools 같은 최적화 라이브러리: 설치가 안 될 수 있고 Docker 이미지가 커진다. 설치되면 비교군으로만 쓴다.
- 한계: 휴리스틱이라 최적이 아니다. 정류장 수가 수백 개를 넘으면 병합 단계가 느려진다(O(R^3)).

## 5. 지표 (기준선과 나란히 보인다)
차량 수 / 승객 탑승 시간 합 / 평균 / 최대 / 정원 사용률 / 조건 위반 수(0 이어야 함).
참고 구현 예제: 직행 7대 > 4대, 평균 탑승 31.7분 > 32.4분, 위반 0. "차량 3대를 줄이는 대신 평균 0.7분 늘었다"처럼 바뀐 것과 대가를 함께 말한다.

## 6. 독립 검사기 (생성 코드와 따로 다시 계산한다)
- 모든 구성원이 정확히 한 노선에 배정됐나(수요 = 배정)
- 정원, 최대 탑승 시간, 도착 시각 <= 근무 시작 - 여유
- 잘못된 계획(정원 초과, 누락)을 넣으면 실제로 잡는지 테스트한다. 실패를 본 적 없는 검사기는 믿지 않는다.
- 손으로 계산할 수 있는 작은 예제(정류장 3개)로 기대값을 따로 만든다.

## 7. 모듈과 상태 (서술형 2번 재료)
```
데이터셋 선택 > 검증(validate_dataset) > 적용(활성 데이터셋 저장)
  > 노선 생성(plan) > 검사(check_plan) > 계획 저장(데이터셋 해시, 조건과 함께)
  > 구성원 화면 조회 > CSV 내보내기
```
- 활성 데이터셋, 조건(정원, 여유, 최대 탑승), 계획은 각각 한 곳에서만 쓴다. 계획에는 어떤 데이터셋과 조건으로 만들었는지 남긴다(데이터셋이 바뀌면 낡은 계획을 표시).
- 화면은 저장된 계획을 읽기만 한다. 계산은 서버 한 곳에서.

## 8. 엣지 케이스 테스트 목록
정원 정확히 같음 / 정원 + 1 / 한 정류장 인원이 정원의 2배 이상 / 최대 탑승 시간 경계 / 구성원 0명인 조 / 자정 넘는 근무 / 정류장 좌표 같음 / 회사와 같은 위치의 정류장 / 검증 실패 데이터셋 적용 시도.

## 9. Docker 함정 (해결하면 디버깅 4칸으로 남긴다)
- 서버를 `127.0.0.1` 로 띄우면 컨테이너 밖에서 안 보인다 > `0.0.0.0`
- 포트: `EXPOSE` 와 `docker run -p` 와 앱 포트가 같은지
- 경로: 작업 폴더 기준 상대경로, 데이터 파일이 이미지에 들어갔는지(`.dockerignore` 확인), 쓰기 경로 권한
- 줄바꿈: 셸 진입 스크립트가 CRLF 면 실행이 안 된다
- 의존성: `requirements.txt` 에 실제로 쓴 패키지가 다 있는지. 이미지를 새로 빌드해 README 명령 그대로 확인한다
- Docker 를 쓸 수 없는 환경이면 로컬 실행으로 검증하고 NOT_RUN 으로 남긴다

## 10. 서술형 답 초안 (실제 숫자와 파일명으로 바꿔 외운다)
1. "직행은 차량이 N대 필요했고, 차량 수만 줄이는 병합은 최대 탑승이 M분까지 늘었습니다. 그래서 비용을 차량 가중치와 승객 탑승 시간 합으로 두고 절약 병합 후 2-opt 와 정류장 옮기기로 개선했습니다. 가중치는 담당자 답(차량 1대 = 승객 X분)으로 정했습니다. 휴리스틱이라 최적은 아니고, 정류장이 수백 개면 느려집니다."
2. 위 7번 흐름을 모듈 이름으로 말한다. 상태를 저장하는 곳과 쓰는 쪽이 하나라는 점.
3. "구현하고 테스트한 것은 A, B, C(테스트 N개, check_plan 위반 0). 가정한 것은 속도 V와 정차 시간 D분입니다. 평가자는 X 명령으로 검사기를 돌려 확인할 수 있습니다."
5. "정류장이 10배가 되면 병합 단계 시간부터 재고, 검사기 위반 0과 기준선 대비 지표를 다시 봅니다. AI 결과는 검사기와 손계산 예제로 판단했습니다."
6. 디버깅 기록 4칸 중 Docker 건을 그대로 말한다.
